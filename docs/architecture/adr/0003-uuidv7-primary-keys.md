# ADR-0003: UUIDv7 primary keys

- Status: Accepted (2026-11-09)
- Date: 2026-11-09

## Context
Sequential integer IDs leak volume and invite enumeration, collide when tenant data is moved to a dedicated database, and cannot be generated by offline clients. Random UUIDv4 keys fragment B-tree indexes.

## Decision
All domain tables use UUIDv7 primary keys (time-ordered, random suffix). Generated in the application (Python 3.14's standard-library `uuid.uuid7()`, via `common.db.ids.uuid7`), so clients can also generate IDs for offline creation later. Global reference tables use their standard natural codes (ISO country/currency codes, permission codes).

## Consequences
- 16-byte keys instead of 8: larger indexes, acceptable at expected scale.
- Index locality close to sequential IDs.
- UUIDv7 reveals creation time to anyone holding the ID; acceptable, since IDs are only shown to authorised users.
- No need for a separate public ID column.

## Alternatives
- Bigint PK + public UUID column: two identifiers to manage everywhere, and it does not solve moving tenants between databases. Rejected.
- UUIDv4: index fragmentation. Rejected.
